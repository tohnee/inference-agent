# Auto-Profiling

Auto-Profiling is the optimization driver for this repository.

The normal workflow is intentionally simple:

1. The user writes or generates one `aim.md`.
2. The runtime validates that aim contract.
3. The runtime establishes baseline/profile/exactness evidence.
4. The runtime routes the work to the right skill lane.
5. The runtime writes a bounded next-candidate plan.
6. The evaluator keeps or rejects the candidate using exactness-first rules.

## Files users should know

- `aim.md`: the only recommended user-edited contract.
- `bootstrap_aim.py`: generates complete aim files for E2E, LLM serving, and CUDA/kernel scenarios.
- `runner.py`: executes the optimization loop.
- `skill_routes.json`: maps `scenario` values to the three underlying skill libraries.
- `aim_schema.json`: defines the required aim fields.
- `templates/state/`: checked-in templates copied into target projects as runtime state.
- `examples/`: legacy scenario-specific aim examples.

## Generate an aim

```bash
python3 bootstrap_aim.py \
  --mode e2e \
  --profile diffusion \
  --project-name demo-diffusion \
  --target-repo-path /path/to/target-repo \
  --output aim.md
```

```bash
python3 bootstrap_aim.py \
  --mode llm-serving \
  --profile vllm \
  --project-name demo-vllm \
  --target-repo-path /path/to/target-repo \
  --output aim.md
```

```bash
python3 bootstrap_aim.py \
  --mode cuda-kernel \
  --profile triton \
  --project-name demo-kernel \
  --target-repo-path /path/to/target-repo \
  --output aim.md
```

CUDA/kernel profiles include `cuda`, `triton`, `cutlass`, and `operator`.

## Run the loop

```bash
python3 runner.py init --aim aim.md
python3 runner.py collect-env --aim aim.md
python3 runner.py baseline --aim aim.md
python3 runner.py autopilot --aim aim.md --iterations 3
python3 runner.py status --aim aim.md
```

`autopilot` writes `next_candidate.md` and `next_candidate.json` into the target repo's `.auto-profiling/` state directory before candidate evaluation.

## Exactness policy

The default mode is `exact-parity`. A performance win is rejected if output correctness, cache semantics, request isolation, or declared algorithmic equivalence fails.

Use `bounded-tolerance` only when the aim explicitly declares equivalent logic and acceptable numeric tolerances.

## Command timeout policy

Long-running install, warmup, baseline, exactness, and profile commands are bounded by the aim contract:

- `max_runtime_per_experiment` is the default timeout source generated by `bootstrap_aim.py`.
- `command_timeout_seconds` can be added to `aim.md` to override that default with a stricter per-command limit.
- A timeout returns `exit_code: 124`, sets `timed_out: true`, preserves any partial stdout/stderr, and fails required command execution with a timeout-specific message.
